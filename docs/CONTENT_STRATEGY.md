Status: Approved direction  
Last updated: 2026-07-26  
Scope: Public narrative, portfolio structure, scripts, discoverability, and future content releases

The factual authority for names, dates, scale, project status, and exclusions is `docs/PROFILE_SOURCE_OF_TRUTH.md`.

## 1. Purpose of the site

The website should serve three connected purposes:

1. Provide a credible destination when someone searches for RTH Tech Services Inc. or Rohan Hare.
2. Showcase real projects, technical judgement, and useful public scripts.
3. Function as a subtle online résumé without looking or reading like a CV or LinkedIn profile.

The desired visitor conclusion is:

> Rohan has substantial hands-on experience, understands both technical systems and operational realities, builds supportable solutions, communicates clearly, and is approachable to work with.

The site should demonstrate that conclusion rather than repeatedly state it.

The site should communicate that Rohan is open to consulting, contract work, and selected technical projects.

Avoid:

- “free consultation” sales language;
- language implying that Rohan is waiting around for work;
- exaggerated claims about expertise or market leadership.

## 3. Voice and editorial rules

### Voice

- First person when Rohan is speaking.
- Calm, direct, practical, and specific.
- Confident through evidence rather than adjectives.
- Professional without sounding sanitized into corporate paste.

### Useful content pattern

> Situation → responsibility → decision → practical result

### Prefer

- “I began my IT career in 2005.”
- “Across Harper Grey LLP, Farris LLP, and RBS LLP, I have worked with…”
- “The constraint was…”
- “I chose this approach because…”
- “The system is in production and continues to evolve.”

### Avoid

- third-person biography language;
- visionary, exceptional, world-class, guru, ninja, thought leader, or similar self-awarded labels;
- long paragraphs containing only technology names;
- copying stale LinkedIn prose;
- claiming ownership of work more broadly than the evidence supports;
- invented metrics, outcomes, or architecture.

## 9. Case-study standard

Each substantial case study should answer:

1. **Context** — what environment or workflow existed?
2. **Problem** — what was manual, fragmented, unreliable, slow, or risky?
3. **Constraints** — security, legacy systems, APIs, budget, data quality, adoption, hosting, confidentiality.
4. **Role** — what Rohan personally analyzed, designed, built, coordinated, or supported.
5. **Solution** — architecture and workflow in plain language.
6. **Key decisions** — why this approach was selected.
7. **Outcome** — measured where evidence exists; otherwise a clear operational result.
8. **Status and roadmap** — production, active build, ongoing program, or under review.
9. **Screenshots** — sanitized images with useful captions.
10. **Confidentiality note** — where demonstration or transformed data is used.

Technology belongs in metadata and explanation, but should not become the entire story.

## 10. Scripts Library strategy

The Scripts Library should demonstrate publication quality, not merely code volume.

Each published script should include:

- clear purpose and use case;
- runtime and prerequisites;
- parameterized inputs;
- help and usage examples;
- safe defaults and dry-run support where applicable;
- useful error handling and logging;
- output examples;
- security and privacy notes;
- sanitization and validation status;
- source link;
- licence and responsible-use guidance.

### SQL roadmap

SQL should become a first-class language. Strong initial candidates include:

- object dependency inventory;
- database, table, row-count, and size inventory;
- index usage analysis;
- month-end snapshot patterns;
- SSRS dataset validation and reconciliation;
- SQL Agent job inventory and failure summary;
- permission and role membership inventory;
- safe substring/token extraction patterns;
- reusable calendar and date-range reporting patterns.

A smaller library of excellent, tested scripts is more credible than a large collection of weak examples.

- canonical URLs;
- Open Graph metadata;
- generated sitemap;
- `robots.txt` pointing to the sitemap;
- Person, Organization/ProfessionalService, and WebSite structured data;
- stable custom-domain handling.

Use natural phrases where relevant:

- IT consultant in Vancouver;
- SQL Server and SSRS reporting;
- legal technology and professional-services reporting;
- Microsoft 365 and SharePoint consulting;
- PowerShell automation;
- custom internal tools;
- systems analysis and technical project delivery.

Do not stuff repeated keywords into public copy.

## 12. Confidentiality and screenshots

All screenshots currently committed to the site repository are sanitized and approved.

Before committing future content:

- remove client and matter identifiers unless explicitly approved;
- remove personal data, domains, tenant IDs, server names, paths, IP addresses, invoice data, and production values;
- use demonstration or transformed data where practical;
- do not rely on blur alone when underlying information may be recoverable;
- review image metadata;
- label demonstration data honestly;
- do not expose security architecture that would materially assist an attacker.
